# Replace borrowed CLIs, add five health sources

The `website-health-analytics` skill needs three kinds of change to be complete and correct. First, it should **own its fetch layer**. All four headline sources (GA4, Google Search Console, Microsoft Clarity and Bing Webmaster Tools) are small, stable REST APIs that need only about 6 to 10 calls per site per day, and the two unpinned single-maintainer Bin-Huang CLIs add supply-chain risk without adding logic. Second, it should **fix correctness bugs that already exist**: GA4 `conversions` is deprecated in favor of `keyEvents`, and the skill ignores the response-quality flags (thresholding, `(other)` rollup, truncation) and the provisional-data markers that both Google APIs now return. Third, it should **add the sources a deploy-correlation tool is blind without**: a no-auth live-site probe (HTTP, TLS, DNS, robots, sitemap, noindex, canonical, security headers), CrUX field Core Web Vitals, Clarity friction metrics, and Bing traffic and crawl data. Clarity is the one source that cannot be handled like the others. Its export API returns only the last 1 to 3 days, allows **10 calls per project per day**, and cannot backfill, so the skill has to snapshot it daily or never have Clarity history at all. AI-citation data (Bing AI Performance, the GSC generative-AI report) has no public API from either vendor as of November 2026, so the skill should stop at a manual reminder and a GA4 AI-referrer proxy. A prioritized change list closes the report.

## Four core APIs fit in about ten calls a day

The table below condenses the per-source facts that drive the design. Each is expanded in the sections that follow.

### GA4: cheap to query, but the skill must read quality flags

GA4 quotas are token-based per property. A standard property gets **200,000 core tokens per day, 40,000 per hour, 14,000 per project per property per hour, and 10 concurrent requests**. Most requests cost 10 tokens or fewer, and passing `returnPropertyQuota: true` returns what each call consumed ([GA4 Data API quotas](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas)). A daily check that compares yesterday with a 7- or 28-day baseline across sessions, engaged sessions, key events, channel, device and top landing page costs tens of tokens, so quota is not a design constraint. The two traps are elsewhere. A 500 or 503 counts against a 10-per-hour server-error quota, and once that quota is exhausted every request from the project to that property is blocked. Since mid-2024, more than 10,000 client errors per 15 minutes also blocks the property temporarily ([Data API changelog](https://developers.google.com/analytics/devguides/reporting/data/v1/changelog)). Retry loops therefore need a hard cap.

Freshness matters more than quota. Daily data on standard properties lands about **12 hours** after the day ends, processing "can take 24–48 hours" with values changing in the meantime, and some hits arrive up to **7 days** late ([GA4 data freshness](https://support.google.com/analytics/answer/11198161)). The skill's existing "provisional for 24–48h" caveat is right but incomplete. Normalization should mark the last two days provisional, re-pull them on the next run, and keep a 7-day re-fetch window rather than treating a stored day as final.

Two correctness gaps exist in the current skill. **`conversions` was deprecated on 2024-05-06** and replaced by `keyEvents`, together with `sessionConversionRate`→`sessionKeyEventRate` and related renames. The Admin `conversionEvents` resource is likewise deprecated in favor of `keyEvents` ([Data API changelog](https://developers.google.com/analytics/devguides/reporting/data/v1/changelog); [Admin API REST](https://developers.google.com/analytics/devguides/config/admin/v1/rest)). The old names still resolve, but the metric table, config thresholds, schema and `normalize-timeseries.mjs` should all move to `keyEvents`, and the normalizer should accept the old name as a migration alias. The skill also ignores response metadata. `subjectToThresholding` means rows may be withheld. `dataLossFromOtherRow` means rows were folded into `(other)`, which is common once a dimension exceeds 500 unique values per day, and `landingPage` does exactly that. `samplingMetadatas` signals sampling ([Reporting data expectations](https://developers.google.com/analytics/devguides/reporting/data/v1/reporting-data-expectations)). The **`dataTruncationReasons` field added on 2026-09-14** lists truncated dates ([changelog](https://developers.google.com/analytics/devguides/reporting/data/v1/changelog)). An anomaly computed on a thresholded or truncated day should be downgraded in confidence, not reported as a regression. The new v1alpha `properties.chat` natural-language endpoint carries an "may show inaccurate information" warning, so it has no place in a deterministic check.

Auth needs two paths. Google Cloud organizations created on or after 2024-05-03 **block service-account key creation by default**, and `gcloud auth application-default login` with gcloud's own OAuth client is usually blocked for Analytics scopes. The workaround is a user-owned Desktop OAuth client plus `set-quota-project` ([Bin-Huang/google-analytics-cli README](https://github.com/Bin-Huang/google-analytics-cli)). The skill should therefore accept a service-account JSON key (RS256 JWT exchange) or an `authorized_user` ADC file (refresh-token exchange). One identity can carry both `analytics.readonly` and `webmasters.readonly`.

### Search Console: compare finalized days, sample URL Inspection

`searchanalytics.query` has gained a lot since the skill was written. It now supports `dataState=all` (fresh, partial data, with `metadata.first_incomplete_date` marking where finalized data ends), `dataState=hourly_all` with an `hour` dimension, `type=webMultimodal`, a `brandedClassification` dimension for eligible properties (data from 2026-02-21), and `filterLists` for multi-country or multi-device filters. The deprecated `searchType` gives way to `type` ([searchanalytics.query](https://developers.google.com/webmaster-tools/v1/searchanalytics/query); [Search Central, Nov 2026](https://developers.google.com/search/blog/2026/11/search-analytics-api-update)). Hourly data arrived in April 2025 with up to 10 days of history via the API ([Search Central blog](https://developers.google.com/search/blog/2025/04/san-hourly-data)). Final data is "typically available after 2–3 days," and the API exposes at most **50,000 rows per day per search type**, sorted by clicks ([Getting all your data](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data)).

The right daily pull is `dataState=all` grouped by `date` over 10 to 14 days. Days at or after `first_incomplete_date` are stored as provisional, and alerts fire only on finalized days. This replaces the skill's fixed `gscWindowDays` heuristic with the API's own marker. Limits are generous for this pattern: 1,200 QPM per site and per user, plus a 10-minute and a daily "load" quota that only page×query grouping over long ranges will hit ([Search Console API limits](https://developers.google.com/webmaster-tools/limits)). The constraint that actually binds is **URL Inspection at 2,000 calls per day and 600 per minute per site**. URL Inspection returns Google's indexed verdict and is the only programmatic substitute for the Rich Results Test, which has no API ([urlInspection.index.inspect](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect); [Google structured data docs](https://developers.google.com/search/docs/appearance/structured-data)). Sample it: the top landing pages, plus URLs touched by the most recent deploy. `siteUrl` must match GSC exactly (`sc-domain:example.com` or a trailing-slash URL prefix), or calls fail.

One interpretive caveat belongs in `metric-definitions.md`. AI Overviews and AI Mode impressions are **folded into the `web` totals**. Google launched a separate generative-AI report in June 2026 ([Search Central blog](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports)), but testers found every candidate API `type` value rejected and no AI-related `searchAppearance` value ([AskedAbout](https://askedabout.com/news/can-you-get-search-console-generative-ai-data-from-the-api)). Google has also confirmed that AI Mode follow-up turns show up as new long, conversational query rows ([Suganthan](https://suganthan.com/blog/ai-mode-queries-search-console/)). Rising impressions with flat clicks may therefore be AI surfaces rather than a CTR regression, and the skill should say so instead of flagging it.

### Clarity: the quota forces a snapshot store

Clarity has one documented aggregate endpoint, `GET https://www.clarity.ms/export-data/api/v1/project-live-insights`. It authenticates with a Bearer JWT that only a project admin can generate (Settings > Data Export) and that is bound to a single project. It accepts `numOfDays` of 1, 2 or 3 (a rolling 24/48/72 hours from call time, not calendar days) and up to three `dimensionN` breakdowns: Browser, Device, Country/Region, OS, Source, Medium, Campaign, Channel or URL. The hard limits are **10 requests per project per day, 1,000 rows per response with no pagination, and UTC timestamps** ([Clarity Data Export API](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-data-export-api)). The daily quota is shared by every token and tool on the project. PostHog's production connector treats a surviving 429 as final, warns that "other tooling" may have consumed the quota, and calls repeated syncs "the only way to accumulate history against this API" ([PostHog connector](https://github.com/PostHog/posthog/blob/master/products/warehouse_sources/sources/microsoft_clarity/microsoft_clarity.py)).

For the skill, that means one no-dimension `numOfDays=1` call at a fixed UTC time, plus an optional `dimension1=URL` call. Together they use at most 2 of the 10 daily calls, and the duct project uses exactly this two-call budget ([duct fetch.py](https://github.com/5hirish/duct/blob/main/backend/service/clarity/fetch.py)). Each raw response is written to a dated snapshot file. The skill also needs a local per-UTC-day call counter, never retries a 429, and records a missed day as a gap: a 2- or 3-day catch-up call returns one aggregate that cannot be split into days. The no-dimension call returns every metric block at once: traffic (sessions, bot sessions, distinct users, pages per session), scroll depth, engagement time, and six friction metrics (dead clicks, rage clicks, excessive scroll, quickbacks, script errors, error clicks). These are the **only client-side UX-regression signals in the stack**, and they map directly to code: a rage-click spike on one URL after a deploy points at a broken button. Field casing differs between Microsoft's sample (`distantUserCount`) and real clients (`distinctUserCount`), and counts arrive as strings ([pig-mesh handler](https://github.com/pig-mesh/pig/blob/master/pig-upms/pig-upms-biz/src/main/java/com/pig4cloud/pig/admin/handler/ClarityFetchTaskHandler.java)), so the parser must match keys case-insensitively and coerce counts to integers.

Two Clarity changes affect interpretation. Since **2025-10-31**, Clarity enforces consent signals for EEA, UK and Swiss visitors. Without a signal it assigns a unique ID per page view and stops stitching sessions ([Consent API v2](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-consent-api-v2)), so pages per session and user counts for those segments collapse for reasons unrelated to any deploy. The official `@microsoft/clarity-mcp-server` reached **v3.0.0 on 2026-11-16**. It defaults to browser OAuth, deprecates Data Export token auth, and talks to an undocumented `clarity.microsoft.com/mcp/*` API whose natural-language dashboard query supports longer ranges, Web Vitals and session recordings ([clarity-mcp-server README](https://github.com/microsoft/clarity-mcp-server/blob/main/README.md)). That is useful for interactive drill-down, and Microsoft ships a Claude connector for it ([Claude connectors](https://claude.com/connectors/microsoft-clarity)). It is a poor fit for an unattended deterministic check because the input is free text, the output is free form, it needs a stored OAuth refresh token, and its quota is unpublished. The skill should use the export API for the daily path and point users to the MCP or connector for "show me recordings with JS errors on /checkout."

### Bing Webmaster Tools: an API key and a `{"d": ...}` envelope

Bing Webmaster Tools offers OAuth 2.0 (scopes `webmaster.read` and `webmaster.manage`) and a per-user API key. Each user can have **only one API key**, and it covers all of that user's verified sites ([Getting Access](https://learn.microsoft.com/en-us/bingwebmaster/getting-access); [OAuth 2.0](https://learn.microsoft.com/en-us/bingwebmaster/oauth2)). The API key is the right choice for a headless check: `GET https://ssl.bing.com/webmaster/api.svc/json/{Method}?siteUrl=...&apikey=...`. Responses are WCF-wrapped in `{"d": ...}` and dates use the `/Date(ms±hhmm)/` format ([GetQueryStats](https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi.getquerystats?view=bing-webmaster-dotnet)). A bad key returns HTTP 400 with `{"ErrorCode":3,"Message":"ERROR!!! InvalidApiKey"}` (live probe of [ssl.bing.com](https://ssl.bing.com/webmaster/api.svc/json/GetUserSites)). The key travels in the query string, so every logged URL must be redacted.

Granularity is uneven, and the anomaly rules have to respect it. `GetRankAndTrafficStats` gives **daily** clicks and impressions across all verticals, including Chat, since 2023-03-24 ([GetRankAndTrafficStats](https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi.getrankandtrafficstats?view=bing-webmaster-dotnet)). `GetCrawlStats` gives daily 2xx/301/302/4xx/5xx counts, robots-blocked pages, malware flags and `InIndex` over 6 months ([GetCrawlStats](https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi.getcrawlstats?view=bing-webmaster-dotnet)). `GetQueryStats` and `GetPageStats` update **weekly**. The daily series should feed z-score detection, and query and page data should only be compared week over week. Neither API lag nor history depth is documented. The UI now shows 24 months ([Search Engine Land](https://searchengineland.com/bing-webmaster-tools-now-with-24-months-of-data-filters-by-country-and-device-and-keyword-trendlines-460413)), but the skill should anchor on the latest day present in the response rather than on "yesterday." A practical set is about seven GETs per site per day: `GetUserSites` (to normalize `siteUrl`), `GetRankAndTrafficStats`, `GetCrawlStats`, `GetCrawlIssues`, `GetFeeds`, `GetQueryStats` and `GetPageStats`. The interface has not changed since 2023-11-14 ([IWebmasterApi](https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi?view=bing-webmaster-dotnet)), which makes a self-built client low-maintenance.

IndexNow is a write path, not a data source. Bing now recommends it as the primary submission method. It accepts up to 10,000 URLs per POST, engines share submissions with each other, and Google is still absent from the participant registry ([IndexNow docs](https://www.indexnow.org/documentation); [searchengines.json](https://www.indexnow.org/searchengines.json)). The health check should only verify that `/{key}.txt` is reachable and contains the key. Submitting changed URLs after a deploy belongs to `astro-seo`. The new **AI Performance** report (preview since 2026-02-10) has no public API. A Microsoft Q&A answer from February said "not right now," and third-party reports still found no methods as of October ([Bing blog](https://blogs.bing.com/webmaster/February-2026/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview); [SER](https://www.seroundtable.com/bing-webmaster-tools-ai-performance-report-40911.html)). Scraping its internal UI API through a signed-in browser is fragile and the skill should avoid it.

## Own the fetch layer; the CLIs pass data through untouched

The argument for dropping the Bin-Huang CLIs is not that they are bad. They are Apache-2.0 TypeScript wrappers over Google's official clients, they cover every endpoint needed, and they run no install scripts. The problem is that they add almost nothing while costing a lot. Both pass responses through "with no transformation or aggregation," so a self-built client gives up only auth, pagination and profile handling. Both were created in March 2026 by a single maintainer, have **39 and 24 stars and a few hundred npm downloads a month**, and use caret or tilde ranges over the very large `googleapis` and `@google-analytics/*` packages ([google-analytics-cli](https://github.com/Bin-Huang/google-analytics-cli); [google-search-console-cli](https://github.com/Bin-Huang/google-search-console-cli); [npm downloads](https://api.npmjs.org/downloads/point/last-month/google-analytics-cli)). Running them unpinned through `npx` means executing whatever version resolves that day with read access to the user's analytics credentials. They also already lag the API: the GSC CLI has no `filterLists` or `brandedClassification` flags and does not list `webMultimodal`. The skill's own normalizer admits the problem in a comment, which says the CLI's JSON shape "isn't part of this skill's contract." A health check whose input format is outside its contract cannot be called correct.

The alternatives are not better for the automated path. Google's official `google-analytics-mcp` is well maintained (about 3.8k stars) but covers GA only, runs as a Python MCP server, and suits interactive use ([google-analytics-mcp](https://github.com/googleanalytics/google-analytics-mcp)). Every GSC MCP server is community-built with little adoption. For Bing, the most mature wrapper, `merj/bing-webmaster-tools`, has about 21 stars, last released in April 2025, and pulls in aiohttp and Poetry for what amounts to seven GETs ([PyPI](https://pypi.org/pypi/bing-webmaster-tools/json)). For Clarity, the one official tool is the MCP server that is moving away from export tokens.

**Language: stay in Node, not the sibling skill's Python.** The research notes lean toward stdlib Python to match `email-domain-reputation`, but the Google service-account flow needs RS256 signing. Python's standard library cannot do that without shelling out to `openssl` or adding a dependency. Node does it natively with `crypto.createSign('RSA-SHA256')` and the global `fetch`, so a zero-dependency Google client of roughly 150 lines is feasible. Node's `tls` and `dns` modules also cover the probe work. The skill's four existing scripts are already `.mjs`, so one runtime keeps the preflight, tests and install story simple. The sibling skill should still be copied for its *conventions*: secrets read from environment variables or a gitignored `.env`, never from committed config; one script per source, each with fixture-based tests; and a single `audit` entry point. For domain-reputation overlap, call its `check_blocklists.py` as an optional subprocess when present rather than reimplementing DNSBL lookups. The Bin-Huang CLIs can remain documented as an optional, **version-pinned** route for ad-hoc admin queries such as audiences and change history. They should not be a hard dependency.

## The live-site probe catches what deploys actually break

The four analytics sources all report after the fact, with delays of hours to days. The most common deploy-caused regressions on a small Astro/Firebase site show up immediately on the live site: a `noindex` left in a layout, a canonical pointing at a staging host, `robots.txt` disallowing `/`, a sitemap that 404s or loses half its URLs, a broken http→https or apex→www redirect, an HSTS or CSP header dropped from `firebase.json`, or an expiring certificate on a custom domain. All of these can be checked with **plain HTTP and no credentials**. The checks are: fetch `robots.txt` and parse it; fetch `sitemap-index.xml`, which `@astrojs/sitemap` emits, then sample its URLs and diff the count against yesterday; for key pages, read `<meta name="robots">`, `X-Robots-Tag`, the canonical host, the title, the `h1` and JSON-LD parse validity; read the security headers; read the TLS `notAfter` date and alert under 21 days; and resolve the apex and www DNS records. Each finding maps to a specific file to fix in the repo, which is exactly the skill's stated goal. It should be the first new script, because it needs no setup and turns the skill from an analytics reader into a deploy-regression detector. A daily run cannot see outages between runs. For that, the skill should read Google Cloud Monitoring uptime checks, free for the first 1 million executions per project ([Cloud Observability pricing](https://cloud.google.com/monitoring/pricing)).

Performance needs two sources, because neither covers both speed and attribution. The **CrUX API** (`POST chromeuxreport.googleapis.com/v1/records:queryRecord`, an API key, 150 QPM, free) returns field p75 values for LCP, INP, CLS, FCP and TTFB. It is a 28-day rolling average about two days behind, refreshed daily around 04:00 UTC ([CrUX API](https://developer.chrome.com/docs/crux/api)). The History API returns up to 40 weekly periods ([CrUX History API](https://developer.chrome.com/docs/crux/history-api)). A deploy regression in CrUX therefore emerges over 1 to 4 weeks. The history endpoint's weekly buckets suit before-and-after-deploy comparisons, and low-traffic pages will usually return "not found," which should read as insufficient data rather than an error. **PageSpeed Insights** lab runs on the homepage and 3 to 5 key templates give the immediate per-deploy signal ([PSI v5](https://developers.google.com/speed/docs/insights/v5/get-started)). Lighthouse scores swing several points between runs, so the skill should alert on audit-level changes (LCP element, render-blocking resources, byte weight) rather than the headline score. Google plans to drop CrUX data from PSI responses, so field data should come only from the CrUX API. PSI quotas are not officially documented, and third-party figures conflict.

Several sources are conditional and should switch on only when the site actually uses them. These are Firebase Hosting's `response_count` by status code once Cloud Logging is linked, which is the best server-side "did the deploy 404 a route" signal ([Firebase Hosting logs](https://firebase.google.com/docs/hosting/web-request-logs-and-metrics)); and a Safe Browsing lookup. The Safe Browsing API is "for non-commercial use only," and commercial sites are directed to Web Risk ([Safe Browsing reference](https://developers.google.com/safe-browsing/reference)), so the skill should either flag the licensing issue or default to a blocklist check through the sibling skill. AI-referral traffic costs almost nothing: a GA4 report of sessions by `sessionSource` for chatgpt.com, perplexity.ai, copilot.microsoft.com and gemini.google.com uses the integration the skill already has.

## Conclusion

The skill's weakest point is not a missing source. It is that the skill does not control its own inputs. It cannot say what shape its GA4 data arrives in, it ignores the flags Google attaches to tell it when numbers are partial or withheld, and it has no way to tell a deploy regression from a platform change, such as AI surfaces inflating impressions or Clarity's consent mode splitting sessions. Bringing the fetch layer in-house, at roughly 500 to 800 lines of zero-dependency Node across four sources, turns all of those into explicit fields the anomaly rules can reason about. It also removes the only part of the skill that executes unvetted third-party code.

The sources differ in time scale, and the skill should treat them that way. The live-site probe sees a broken deploy within minutes. GA4 sees it within about 12 hours, Clarity within 24 rolling hours, GSC and Bing within 2 to 3 days, and CrUX over weeks. A correlation engine that knows each source's lag can do better than "something dropped after commit X": it can check whether the probe failed first, whether friction rose before traffic fell, and whether search impressions followed. That sequence is the strongest evidence a root-cause claim can have. Two gaps remain unverified and should be confirmed with one live call during implementation: the exact Clarity field names and Country dimension string, and the response shapes of Bing's `GetCrawlIssues` and `GetFeeds`.
